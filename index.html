Engineering decisions

What I chose and why

Every architecture decision has a tradeoff. These are the ones that mattered most on this project.

Prototype in vanilla HTML before migrating to React
Build strategy
Validated all eight features and the full AI integration in a single file before committing to a component architecture. This meant the React migration was a structural exercise, not an exploratory one - every component had a known shape and behaviour before a line of JSX was written.
Outcome: Zero feature regressions during migration. All 59 tests written against behaviour that was already proven to work.
Vercel + Render + Neon over a single managed platform
Platform
Railway would have been simpler - one dashboard, one bill. I chose the free split deliberately: Vercel for static assets, Render for the API, Neon for Postgres. Each platform is best-in-class for its layer, the total cost is $0, and the architecture maps cleanly to how most scale-ups actually run production infrastructure. The tradeoff is operational complexity - three platforms to monitor instead of one.
Outcome: Production infra running at $0/month. Architecture mirrors real-world patterns that engineers on any team will recognise.
Proxy auth through Vercel rather than accept a browser workaround
Quality bar
Cross-domain OAuth between Vercel and Render triggered Chrome's third-party cookie blocking. The fast fix was to document the workaround and tell users to adjust browser settings. Instead, I restructured the deployment so all auth routes proxy through Vercel - making the session cookie first-party and invisible to cookie blocking. One more hour of work; zero friction for every future user.
Outcome: Login works out of the box on all browsers with default settings. No documentation needed.
Full test suite before deployment, not after
Engineering culture
59 tests across store logic, API helpers, UI components, and user interactions - all written before the first production deploy. The suite caught two real bugs during the auth layer addition: a Sidebar component that would crash without a mock auth context, and a jsPDF v4 constructor change that broke the PDF export mock. Both would have been silent failures in production.
Outcome: Clean deploys from day one. CI blocks any push that breaks the suite.
Architecture

System design

Separation of concerns across three independent layers, with the frontend never holding secrets or talking directly to external APIs.

Vercel (React/Vite) -- /api, /auth --> Render (Express) -- pg --> Neon (Postgres)
+-- proxies --> Anthropic Claude API
The browser talks only to the Vercel origin. /api and /auth are proxied server-side - session cookies stay first-party, secrets never reach the client, and the backend can be swapped or scaled independently of the frontend. OAuth credentials, the Claude API key, and database connection strings live only in the backend environment.

How I work

Engineering principles this project reflects

01
Fix root causes, not symptoms
Every time a workaround was available, I took the time to fix the underlying problem instead. Cross-domain cookies, cold-start UX, duplicate OAuth accounts - each got a proper fix. Workarounds compound into products nobody wants to maintain.
02
Validate before you invest
The HTML prototype forced every product decision before any architecture decision. The cheapest time to change a feature is before you've built the infrastructure around it.
03
Testing is a delivery accelerator
59 tests written before deployment meant every subsequent change - auth addition, OAuth fix, dependency upgrade - could be made confidently. The suite paid back its cost within the first week of changes.
04
Architecture decisions are business decisions
Choosing $0/month infrastructure over a paid platform wasn't just cost optimisation - it was demonstrating that engineering judgment includes understanding constraints and making deliberate tradeoffs, not just picking the most convenient option.
Reflection

What this project taught me about leading AI product development

"The engineering work on this project was straightforward. The judgment work was harder. When to prototype vs architect. When to fix vs ship. When the simple platform is the right call and when it creates problems later. These are the decisions that determine whether an engineering team builds the right thing well or the wrong thing fast."

"AI integration changes the product development loop in a specific way: Claude can generate a working feature in seconds, which means the bottleneck shifts from writing code to knowing what to build, how to structure prompts, how to handle streaming and structured output reliably, and how to test AI-dependent behaviour without making tests brittle or expensive. None of that is obvious until you've done it."

"The cross-origin auth problem is a good example of the kind of issue that appears late, looks like a browser quirk, and has an easy workaround that accumulates technical debt. I've seen this pattern at every company I've worked at - the workaround gets shipped, documented, and forgotten, and six months later nobody knows why users on certain browsers can't log in. The right call is almost always to fix it properly, even when the deadline argues otherwise."
