Engineering decisions worth noting

The choices that shaped the system

Every decision below had a tradeoff. I've tried to be specific about what each one cost and what it bought.

Prototype in vanilla HTML before committing to React
All eight features were validated in a single HTML file before a component was written. This meant the React migration was structural rather than exploratory - every component had a known shape before any JSX was touched. The alternative was discovering mid-architecture that a feature didn't work the way I'd imagined it.
Decision: validate the product before investing in the architecture
Three-platform hosting over a single managed service
Railway would have been simpler - one dashboard, one bill. I chose Vercel for the frontend, Render for the API, and Neon for Postgres instead. Each is best-in-class for its layer, the total cost is $0, and the separation maps cleanly to how most scale-ups actually run production infrastructure. The tradeoff is operational complexity across three platforms. That complexity is deliberate: it surfaces the real concerns a team would face at scale, rather than hiding them behind a managed abstraction.
Decision: real-world architecture over developer convenience
Fix the cookie problem at the infrastructure layer, not the user layer
Cross-domain OAuth between Vercel and Render triggered Chrome's third-party cookie blocking. The fast fix was to document a workaround and tell users to adjust their browser settings. Instead I restructured the deployment: all auth routes proxy through Vercel, making the session cookie first-party and invisible to browser restrictions. One more hour of engineering. Zero friction for every future user, regardless of browser or settings.
Decision: fix the root cause; workarounds compound into products nobody wants to use
Centralise job persistence in a service layer after a bug exposed scattered state
A bug shipped where adding or moving a job updated the UI but silently failed to persist - the data vanished on reload. The immediate fix was to add the missing API call. Instead I traced it to the structural cause: persistence was wired per-handler across the codebase, so any new action could forget to save and the test suite wouldn't catch it. I moved all job mutations into a single service module where every action updates local state and the backend together, making the omission impossible to express. I then retrofitted the tests to assert the API was actually called, not just that the UI updated - so the whole class of bug is guarded against, not just the instance that surfaced.
Decision: structure the code so the wrong thing is hard to write, then test the right thing
Rate limit the AI proxy before sharing the demo publicly
The live demo uses a real Anthropic API key. Without rate limiting, one curious visitor running all eight features repeatedly could generate meaningful cost. Before publishing the showcase, I added per-user burst and daily caps (10 calls/minute, 100/day) on the backend, with the frontend surfacing a clean error rather than a generic failure when the limit is reached. Small measure, significant protection, zero UX friction for normal use.
Decision: production thinking applies even to portfolio demos
Build the test suite before deployment, then grow it to guard against regressions
92 tests were established before the first production deploy and grown as features were added. The suite caught two real bugs during the auth layer addition: a Sidebar component that would crash without a mock auth context, and a jsPDF v4 constructor change that broke PDF export. Both would have been silent production failures. More importantly, when persistence was centralised into the service layer, the refactored tests could assert that the API was actually called - not just that local state changed. A test suite that only checks the UI updated is a false sense of confidence.
Decision: test the right thing, not just the convenient thing

How Claude is used

Six distinct AI workflows

Claude is called from a secure, rate-limited backend proxy. The API key never touches the browser. User content is boundary-separated from instructions in every prompt to guard against injection.

Streaming
Bullet generator and cover letter - tokens stream directly to the UI as they arrive. The resume store is injected as context on every call. Streaming makes output feel instant and gives the user something to read before the response completes.
Structured JSON
Keyword matching and resume scoring - prompts return strict JSON (matched/missing keywords, scores, feedback arrays) parsed against an expected schema. If the response doesn't match, it's rejected rather than salvaged. The detailed scorer returns five headline dimensions and seven sub-scores in a single call.
Write-back
Auto-tailor resume - Claude rewrites the summary and skills sections to include missing JD keywords, then updates the persisted resume directly. This is the highest-risk prompt in the app: it takes a job description the user copied from an external site and uses it to modify stored data. User content is fenced in explicit delimiters with an instruction that it is data to process, not instructions to follow.
Personalised
Interview prep - the full resume text is injected into the prompt so questions are tailored to the candidate's actual background and experience, not generic behavioural templates.
Architecture

How the system is structured

Vercel (React/Vite) -- /api, /auth --> Render (Express) -- pg --> Neon (Postgres)
+-- proxies --> Anthropic Claude API
The browser talks only to the Vercel origin. /api and /auth are proxied server-side - session cookies stay first-party (eliminating third-party cookie blocking across all browsers), secrets never reach the client, and the backend can be scaled or swapped independently. The AI endpoints sit behind authentication and per-user rate limits. OAuth credentials, the Claude API key, and the database connection string live only in the backend environment.

Reflection

What this project taught me about leading AI product development

"The engineering work on this project was not the hard part. The hard part was judgment - when to prototype vs architect, when to fix vs ship, when the simple platform choice is the right call and when it will create problems later. These are the decisions that determine whether an engineering team builds the right thing well or the wrong thing fast."

"AI integration changes the product development loop in a specific way: the bottleneck shifts from writing code to knowing what to build, how to structure prompts, how to handle streaming and structured output reliably, and how to test AI-dependent behaviour without making tests brittle or expensive. None of that is obvious until you have done it."

"The persistence bug is the example I keep returning to. The immediate fix was one line. The right fix was a service layer, retrofitted tests, and a documented rationale - three things that take longer and produce no new features. That is the call a Head of Engineering makes every day: fix the instance or prevent the class. The answer depends on how much the class costs you, and you only develop that intuition by shipping things and living with the consequences."
